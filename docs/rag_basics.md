# RAG 检索增强生成基础

## 什么是 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与
大语言模型生成结合的技术架构。它的核心思想是：在 LLM 生成回答之前，
先从外部知识库中检索相关内容，把检索结果作为上下文注入提示词，
让模型基于真实数据作答，而不是仅凭训练时的记忆。

RAG 主要解决三个问题。第一是大模型的幻觉问题，模型在缺乏事实依据时
会编造看似合理但错误的内容。第二是知识时效性问题，大模型的训练数据
有截止日期，无法回答最新发生的事件。第三是私有数据访问问题，企业的
内部文档、产品资料、客户数据无法在训练阶段进入通用模型。

## RAG 的核心流程

一个标准的 RAG 系统包含两个阶段：索引阶段和检索阶段。

索引阶段发生在用户提问之前。首先把原始文档加载进来，可能是 PDF、
Markdown、Word 或 HTML 格式。然后进行文本切分，把长文档拆成大小
合适的片段（chunk）。接着用嵌入模型把每个片段编码成向量，存入向量
数据库。这个过程通常只需要做一次，之后文档更新时增量重建即可。

检索阶段发生在用户提问时。首先把用户问题用同一个嵌入模型编码成
查询向量。然后在向量数据库中做相似度搜索，找出距离最近的 Top-K
个片段。可选地做重排序（rerank），提升相关性。最后把检索到的片段
拼接进提示词，交给 LLM 生成最终回答。

## 文本切分策略

文本切分是 RAG 系统里最容易被低估的环节。切得太粗，检索结果会包含
大量无关信息，浪费上下文窗口；切得太细，片段会丢失完整语义，模型
难以理解。常见的切分策略有以下几种。

固定长度切分最简单，每 N 个字符切一刀。缺点是会切断句子和段落，
破坏语义完整性。段落切分按空行或换行符拆分，保留段落边界，适合
结构清晰的文档。递归切分是 LangChain 的默认策略，按段落、句子、
字符逐层回退，尽量保持语义完整。语义切分用嵌入模型判断相邻句子
的相似度，在语义转折处切分，效果最好但计算成本高。

无论用哪种策略，通常都会加一定比例的重叠（overlap）。比如每个
chunk 长度 300 字符，相邻 chunk 之间重叠 50 字符。这样可以避免
关键信息正好落在切分边界上而被割裂。经验值是 10% 到 20% 的重叠。

## 嵌入模型选型

嵌入模型决定了文本向量化的质量，直接影响检索效果。选型时需要考虑
几个维度：语言支持、向量维度、推理速度、模型大小。

对于中文场景，英文模型效果很差。比如 all-MiniLM-L6-v2 是 ChromaDB
的默认模型，但它只支持英文，中文文本编码后向量质量低，检索距离
普遍偏高。中文场景推荐 BAAI/bge-small-zh-v1.5 或
BAAI/bge-large-zh-v1.5，前者约 100MB 适合本地部署，后者约 1.3GB
效果更好但资源占用高。

多语言场景可以考虑 paraphrase-multilingual-MiniLM-L12-v2 或
text-embedding-3-small（OpenAI）。前者免费且支持 50 多种语言，
后者效果优秀但需要 API 调用，有成本和隐私考虑。

向量维度影响存储和检索速度。常见维度是 384、768、1024。维度越高
表达能力越强，但存储和计算成本也越高。大多数场景 384 或 768 维度
已经够用。

## 向量数据库

向量数据库专门用于存储和检索高维向量。它的核心能力是近似最近邻
搜索（ANN），能在百万级甚至亿级向量中快速找到最相似的 Top-K。

常见的向量数据库包括 ChromaDB、Milvus、FAISS、Qdrant、Weaviate、
Pinecone 等。ChromaDB 轻量易用，适合原型和中小规模场景，支持
持久化和增量索引。Milvus 功能完整，适合大规模生产环境。FAISS 是
Facebook 开源的高性能库，通常作为底层引擎使用。Qdrant 用 Rust
编写，性能优秀且 API 友好。

选择向量数据库时考虑几个因素：数据规模、查询延迟、部署复杂度、
持久化需求、生态集成。小规模原型优先 ChromaDB，生产环境根据
团队技术栈和运维能力选择。

## 相似度度量

向量检索的核心是相似度计算。常见的度量方式有四种。

余弦相似度（Cosine Similarity）计算两个向量夹角的余弦值，范围
-1 到 1，值越接近 1 表示越相似。它只关注方向不关注长度，适合
文本语义匹配，是 RAG 最常用的度量。

欧氏距离（L2 Distance）计算两个向量的直线距离，值越小越相似。
ChromaDB 默认用 L2 距离的平方，值域无上界。

内积（Inner Product）计算向量点积，适合归一化后的向量，此时
等价于余弦相似度。

曼哈顿距离（L1 Distance）计算各维度差值的绝对值之和，较少用于
文本检索。

选择度量方式时要和嵌入模型匹配。大多数句向量模型训练时用余弦
相似度，所以检索时也用余弦距离效果最好。ChromaDB 创建集合时可以
通过 metadata={"hnsw:space": "cosine"} 指定，默认是 l2。

## 距离阈值过滤

检索到的 Top-K 结果不一定都相关。如果知识库里没有用户问的内容，
强行返回 K 个片段反而会误导 LLM。所以需要设置距离阈值，超过阈值
的片段直接丢弃。

余弦距离下，0 表示完全相同，2 表示完全相反。经验阈值是 0.3 到 0.6。
0.3 以内算高度相关，0.3 到 0.5 算相关，0.5 以上通常不相关。具体
阈值需要根据嵌入模型和实际数据调优，不能拍脑袋定。

阈值太严会漏掉相关结果，太松会引入噪声。建议先用一批测试问题
观察距离分布，再决定阈值。

## 增量索引

生产环境的 RAG 系统，文档会不断更新。每次都全量重建索引既慢又
浪费资源。增量索引通过比对文件哈希，只重建改动过的文档。

具体做法是维护一个文件名到哈希的映射。每次同步时，遍历文档目录，
计算每个文件的当前哈希。如果某文件哈希变了，删除它在向量库里的
旧片段，重新切分和向量化。如果某文件被删了，删除它对应的所有片段。
新增文件直接索引。

增量索引的关键是删除操作的实现。ChromaDB 支持按 metadata 过滤
删除，比如 collection.delete(where={"source": "file.md"})。只要
每个片段都带了 source 元数据，就能精准删除。

## RAG 的常见问题

检索质量差是最常见的问题。原因可能是嵌入模型不合适、切分策略
不合理、距离阈值设置不当。排查时先看检索到的片段是否相关，再
看距离值分布，逐层定位。

上下文过长是另一个问题。如果 Top-K 设得太大，或者片段本身很长，
拼接后的上下文会超过模型窗口限制，导致报错或截断。解决方案是
限制单片段长度、控制 Top-K 数量、对检索结果做压缩。

幻觉问题在 RAG 里仍然存在。模型可能忽略检索结果直接作答，或者
错误解读检索内容。可以在系统提示词里强制要求基于检索结果回答，
并在检索不到时明确说明。

## 高级 RAG 技术

Query Rewrite：用户问题往往表述模糊，直接用原问题检索效果差。
可以先让 LLM 改写问题，生成多个查询变体，提升召回率。

HyDE（Hypothetical Document Embeddings）：先让 LLM 生成一个
假设的回答，再用这个回答去检索。假设回答的语义更接近真实文档，
检索效果往往比原问题好。

Hybrid Search：结合向量检索和关键词检索（BM25），取长补短。
向量检索擅长语义匹配，关键词检索擅长精确匹配，混合后召回率
更高。

Reranker：用专门的交叉编码器模型对 Top-K 结果重新排序。交叉
编码器同时看问题和文档，判断相关性更准，但计算成本高，所以
通常只在粗排后的少量候选上使用。

Parent-Child Retrieval：索引时切分小块（child）用于检索，但
返回时返回大块（parent）给 LLM。兼顾检索精度和上下文完整性。

Context Compression：对检索结果做摘要或压缩，去掉冗余信息，
把最相关的部分注入提示词。

## 总结

RAG 是一套工程化程度很高的技术。核心挑战不在于调 API，而在于
每个环节的细节调优：切分策略、嵌入模型、距离阈值、Top-K 数量。
这些参数没有标准答案，需要结合具体数据和业务场景实验。

一个可用的 RAG 系统，检索距离应该在合理范围内（余弦 0.3 到 0.5），
检索结果和问题语义相关，LLM 能基于检索结果给出准确回答。达不到
这些标准时，逐层排查：先看切分是否合理，再看嵌入模型是否合适，
最后看阈值和 Top-K 是否调对。
